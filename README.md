# Кинозал — агент по раздачам kinozal.me

Локальный веб-агент, который по просьбе в чате находит раздачи на kinozal.me,
скачивает `.torrent`, ставит его в Transmission и умеет **следить за новыми
сериями** параллельно по любому числу задач.

Сайт: `https://<IP-мака>:8000/` (проброс порта — снаружи; локально
`https://127.0.0.1:8000/`).

---

│   ├── parsing.py        разбор названий: качество, озвучка, сезон, серия
│   ├── matching.py       фильтрация, ранжирование, «что такого нового»

├── web/
│   ├── app.py            FastAPI: только транспорт (вход, JSON, SSE, статика)

**Агент независим от интерфейса.** Всё поведение — в `core/agent.py`; он отдаёт
объекты `Turn` с кнопками `Action`. Веб их рисует, но точно так же их сможет
отрисовать Telegram-бот: `agent.handle_message(session, text, mode)`,
`agent.handle_action(session, kind, payload)`, `agent.list_tasks()`,
`agent.cancel_task(id)`. Проверяется это тем, что `core/cli.py` работает без
сервера и без браузера.

## 2. Быстрый старт

```bash
cd ~/torrent-checker
scripts/run.sh start          # поднимет шлюз и сайт, выпустит сертификат
scripts/run.sh status         # состояние, адреса, проверка /health
scripts/run.sh logs           # последние строки логов
scripts/run.sh stop|restart
scripts/run.sh cert           # перевыпустить самоподписанный сертификат
```

Адрес: **https://<IP-мака>:8000/** — IP задаётся в `.env` (`SITE_TLS_NAMES`,
`PUBLIC_URL`), пароль входа — `SITE_PASSWORD`.
Браузер один раз предупредит о самоподписанном сертификате — это ожидаемо.

Зависимости (уже установлены в `.venv`):

```bash
.venv/bin/pip install -r requirements.txt
cd mcp/kinozal-mcp && npm install && npm run build
```

## 3. Как это работает

### 3.1 Два процесса

| Процесс | Порт | Зачем |
|---|---|---|
| `web.app` (uvicorn, HTTPS) | `0.0.0.0:8000` | сайт; слушает все интерфейсы, иначе проброс порта бесполезен |
| `services.gate_service` | `127.0.0.1:8123` | обход Cloudflare; наружу не выставляется |

### 3.2 Cloudflare — главная сложность kinozal.me

`browse.php`, `details.php`, `login.php`, `download.php` закрыты managed-challenge
Cloudflare: `curl`, `httpx`, `node-fetch`, `curl_cffi` с любым `impersonate` и
headless-браузеры получают `403` и страницу «Just a moment…». Проходит только
**настоящий Chrome**, который исполняет JS-задачу.

Отсюда схема шлюза (`services/cf_gate.py`):

1. Chrome запускается через CDP (`nodriver`), окно сдвинуто за экран
   (`--window-position=-2400,-2400`), профиль — `data/chrome-profile`.
2. Chrome проходит challenge и получает cookie `cf_clearance`.
3. Дальше по сайту ходит `curl_cffi` с этим cookie и User-Agent браузера —
   десятки миллисекунд вместо секунд.
4. Протух `cf_clearance` → шлюз видит `403`/`cf-mitigated`, будит браузер,
   проходит challenge заново и повторяет запрос.
5. Вход на трекер (`POST /takelogin.php`) делает **браузер**: этот POST
   Cloudflare у обычного клиента отбивает.

Проверено, что headless не работает вообще (`GATE_HEADLESS=1` — не поможет),
поэтому по умолчанию окно «настоящее», но за пределами экрана.

### 3.3 MCP

Взят [tokezooo/kinozal-mcp](https://github.com/tokezooo/kinozal-mcp) и лежит
форком в `mcp/kinozal-mcp`. Изменения:

* `BASE_URL` → `https://kinozal.me` (зеркало из задачи);
* транспорт: вместо `node-fetch` напрямую — через шлюз (`KINOZAL_GATE_URL`),
  потому что иначе Cloudflare не пускает;
* `download_torrent`: логин выполняет шлюз, файл приходит в base64 и
  проверяется на bencode (иначе вместо `.torrent` сохранилась бы HTML-страница
  «Вход»); если трекер вместо файла отдал страницу с уведомлением (например,
  исчерпан дневной лимит торрент-файлов), из неё достаётся фраза-причина;
* новый инструмент `get_file_list`: список файлов раздачи со страницы
  (AJAX `get_srv_details.php?action=2`). На kinozal.me число `.torrent`
  в сутки ограничено, а состав файлов нужен уже для карточки — поэтому
  карточка и выбор серий показываются без траты лимита, а `.torrent`
  качается только когда человек нажимает «Скачать»;
* разбор страницы раздачи переписан под разметку `.me` (шапка блоками,
  техданные из `#tabs`, размер/сиды/даты из бокового списка).

Инструменты: `search_torrents`, `get_torrent_details`, `get_file_list`,
`download_torrent`. Агент общается с ними по MCP-протоколу через stdio
(`core/mcp_client.py`), поэтому второй трекер добавляется как второй MCP-сервер,
без правок ядра.

`get_torrent_details` вызывается по кнопке «Подробнее» (`Agent.torrent_details`,
маршрут `GET /api/torrent/<id>/details`): страница раздачи — единственный
источник жанра, режиссёра, актёров, описания и строк «Видео»/«Аудио» (там видно
5.1 или стерео, x264 или x265). Поиск этот инструмент не дёргает: лишний поход
через шлюз на каждом запросе никому не нужен, поэтому подробности запрашиваются
только по нажатию и кэшируются на 10 минут.

### 3.4 Модель

DeepSeek `deepseek-flash` (DeepSeek-V4.1-Flash), ключ в `.env`.
Размышления выключены параметром `"thinking": {"type": "disabled"}` — без него
модель возвращает `reasoning_content` и тратит на него время.

Модель делает две вещи:
1. **разбирает запрос** в строгий JSON (название, качество, озвучка, сезон,
   серия, период, «качать сразу или только сообщать»);
2. **формулирует тексты** ответов.

Выбор конкретной раздачи делают правила (`core/matching.py`), а не модель:
одинаковый запрос даёт одинаковый результат, а «4к» не превращается в что попало.

### 3.4-бис Куда качаем: только внешний диск

Загрузки всегда идут на внешний SSD. Путь задаётся `TRANSMISSION_DOWNLOAD_DIR`
(по умолчанию `/Volumes/EAGET/torrents`) и передаётся **в каждом** `add_torrent`
явно — правка настроек в самом Transmission не сможет увести файлы на системный
раздел. Дополнительно агент один раз за процесс переводит на этот диск общие
настройки клиента (`download_dir` и `incomplete_dir`), чтобы торренты,
добавленные руками, тоже ложились туда.

Перед постановкой в очередь проверяются две вещи:

1. **Диск смонтирован.** Если `/Volumes/…` нет, раздача не ставится: агент
   говорит «внешний диск не подключён» вместо того, чтобы молча залить 40 ГБ
   на внутренний. Проверка — именно `ismount`, а не «каталог существует».
2. **Места хватает.** Точный размер берётся из `.torrent` (bencode:
   `info.length` или сумма `info.files[]`), к нему добавляется резерв
   `TRANSMISSION_MIN_FREE_GB` (по умолчанию 5 ГБ). Не хватает — в чат приходит
   сообщение вида «нужно 36,8 ГБ + резерв 5 ГБ, свободно 12,3 ГБ (не хватает
   29,5 ГБ)», раздача **не** попадает в очередь и **не** запоминается как
   скачанная, а под сообщением есть кнопка **«Поставить в очередь»** — она
   повторяет попытку с уже скачанным `.torrent`, без повторного поиска.
   То же уведомление уходит в центр уведомлений, в систему и в Web Push.

Свободное место видно заранее: в карточке подтверждения («Качать буду на
«EAGET», свободно 223,5 ГБ из 223,5 ГБ») и в панели «Служебное».

### 3.4-бис Демон занят диском: панель не врёт и не обнуляется

Transmission отдаёт JSON-RPC из того же потока, которым пишет куски на диск.
Пока идёт большая запись (4K-сезон на внешний SSD — это сотни мегабит в
секунду), ответа на запросы может не быть секундами. Это **не** поломка связи:

* в панели вместо красного «Transmission не ответил» появляется жёлтое
  «занят записью на диск · данные от 19:04», а цифры диска остаются от
  последней удачной проверки (с пометкой, когда их снимали);
* опрос при этом не штормит: после обрыва включается пауза, обычные запросы
  падают сразу, а «прощупывающий» (короткий бюджет, без повтора) проверяет,
  ожил ли демон;
* список «Скачано» не пустеет: он приходит из памяти и подписывается «список от
  NN:NN, проценты не обновляются».

Если демон всё-таки завис намертво (процесс в непрерываемом ожидании диска), в
панели «Служебное» есть кнопка **«Перезапустить Transmission»**: она гасит
процесс (SIGTERM, при необходимости SIGKILL), поднимает приложение заново,
возвращает настройки сессии и честно пишет, сколько ждали. Начатые закачки
продолжатся, но Transmission может перепроверить частичные файлы — на большом
сезоне это занимает время.

Чтобы этого не случалось, агент сам ставит в Transmission два предела:
`TRANSMISSION_SPEED_LIMIT_MBPS` (по умолчанию 70 МБ/с) и
`TRANSMISSION_CACHE_MB` (32 МБ).

### 3.4-тер Контекст переписки и уточнения

Модель разбирает запрос не в вакууме: ей передаётся **скользящее окно** из
последних `CONTEXT_MESSAGES` сообщений (по умолчанию **20**) и состояние текущей
задачи. Поэтому уточнение работает словами:

```
вы:    Тед Лассо
агент: В раздаче 10 серий — какую качать?  [Серия 1] … [Серия 10]
вы:    нет, нужен 4K
агент: Уточнил: качество: 2160p. Смотрю по уже найденным раздачам.
```

**Каждая задача — отдельный чат.** У задачи своя переписка (`messages.task_id`)
и свой контекст для модели: открываете задачу в картотеке — в чате появляется её
история, и уточнения относятся только к ней. Кнопка **«Новая задача»** — внизу картотеки, на всю ширину и на уровне поля
ввода (на телефоне — «＋» в строке ввода) — начинает чистый чат; при открытии сайта
поднимается последняя задача. На телефоне список обновляется свайпом вниз
(когда чат прокручен вверх), потянуть за шапку «Кинозал» — перезагрузить
страницу целиком, а открытая панель и «Киножурнал» закрываются кнопкой
«назад» — она не уводит со страницы. В «работе» — всё, что не закрыто (поиск, ожидание
ответа, скачивание, мониторинг), в «завершённых» — отменённые и скачанные.

Периодическая задача не зависит от того, есть ли уже раздачи: можно завести её
на сериал, который ещё не вышел. Она встанет в мониторинг, будет проверяться по
расписанию и раз в сутки тихо сообщать «пока ничего нет, продолжаю следить»,
а при появлении — уведомит (или сразу скачает, если так задано).
Внутри открытой задачи новых задач не появляется: другое название — это правка
этой же задачи (поиск идёт заново, история остаётся). Новая задача — только
кнопкой «Новая задача». Старая метка `context_from:<сессия>` остаётся как
страховка: после отмены задачи и перед скачиванием окно всё равно обнуляется.

**Но правится только то, что ещё не решено.** Пока задача в выборе — идёт поиск,
предложены качество/озвучка/серии, ждём подтверждения — текст в поле ввода
уточняет её. Как только задача **в работе** (скачивается или мониторится) или
**закрыта** (скачана, отменена, не нашлось, ошибка), править её нельзя: отправка
текста делает то же, что кнопка «Новая задача» — открывается чистый лист, а в
ответе честно написано, что старая задача не тронута:

```
чат: «Брестская крепость»   ← задача качается, открыта в панели
вы:    Тед Лассо
агент: Сейчас качается «Брестская крепость» (14,4 %) — эту задачу не трогаю
       и не правлю. Начинаю новую: «Тед Лассо».
```

Без этого открытая карточка «перетягивала» на себя новый запрос: качающаяся
задача превращалась в другую, раздача оставалась в Transmission, а в ассистенте
её больше не было видно. Если в тексте нет названия («а можно 4K»), задача не
заводится — ассистент просит название, но чистый лист всё равно открывает.

Что происходит под капотом:

* окно = последние 20 сообщений сессии (длинные ответы агента обрезаются до 400
  символов), плюс строка вида «Текущая задача: «Тед Лассо», состояние
  awaiting_choice, параметры: title=…, quality=…»;
* модель возвращает разобранные параметры **и** флаг `refine` — «это уточнение,
  а не новая задача»;
* решение всё равно проверяется правилами (`_is_refinement`): сообщение без
  названия («нужен 4K», «7 серия», «не то») — уточнение к активной задаче; то же
  название — тоже уточнение; **другое название — новая задача**;
* перед всеми правилами стоит проверка `_can_edit`: задача в состоянии
  `searching`, `awaiting_choice`, `awaiting_confirm`, `awaiting_setup` правится,
  остальные (`downloading`, `monitoring`, `done`, `cancelled`, `failed`,
  `not_found`) — нет: текст заводит новую задачу, а ответ помечается
  `start_new`, чтобы интерфейс открыл чистый лист;
* уточнение сливается с параметрами активной задачи (`quality`, `voice`,
  `season`, `episode_from`, `year`, `title`), задача помечается «Уточнил: …»;
* если название не менялось — **нового поиска нет**: перебираются уже найденные
  раздачи (быстро и без лишних запросов к трекеру); если название поменялось —
  поиск идёт заново.

Активной считается незакрытая задача этой сессии в состоянии
`awaiting_choice`, `awaiting_confirm`, `not_found` или `awaiting_setup`. Ответы
на вопросы («что ты умеешь?») тоже получают контекст — последние 10 сообщений.

### 3.5 Жизненный цикл задачи

```
поиск → выбор варианта → подтверждение → скачивание → готово
   │           │                 │
   │           └── кнопки «1080p», «720p», «LostFilm»… (из того, что реально есть)
   └── ничего не найдено → «Сделать периодической»

периодическая: подтверждение («качать сразу» / «только сообщать») → мониторинг
```

Состояния: `searching`, `awaiting_choice`, `awaiting_confirm`, `downloading`,
`monitoring`, `done`, `not_found`, `failed`, `cancelled`.

Если качество или озвучка не названы, агент смотрит, что реально есть на
трекере, и предлагает выбрать **из имеющегося** (одно значение подставляет сам,
чтобы не спрашивать зря). Если ничего нет — честно говорит и предлагает сделать
задачу периодической.

### 3.5-тер Опечатки и «возможно, вы имели в виду»

Трекер ищет по всем словам запроса, поэтому «битва экстрасенсов реванш» даёт
ноль, хотя на трекере есть «Экстрасенсы. Реванш». А иногда наоборот: находит
«Битва экстрасенсов» — другой сериал, и пользователь рискует скачать не то.

Агент разбирает такие запросы в два шага (`core/suggest.py`):

1. **Укороченные варианты запроса.** Из исходного текста строятся скользящие
   окна по словам («экстрасенсов реванш»), варианты без первого и без последнего
   слова, самое длинное слово. Если исходный запрос ничего не нашёл — они ищутся
   на трекере.
2. **Похожесть названий.** Найденное сравнивается с исходным запросом:
   отношение последовательностей, покрытие слов (с учётом форм:
   «экстрасенсов» ≈ «экстрасенсы») и отдельно покрытие «хвоста» запроса — в
   названиях важные слова обычно в конце. Лишние слова в названии дают штраф.

Результат виден в двух случаях:

* **ничего не нашлось** — «По запросу «…» на kinozal.me ничего не нашлось.
  Возможно, вы имели в виду: 1. Экстрасенсы. Реванш …» и кнопки с названиями
  (плюс «Искать как написал» и «Следить за этим названием»);
* **нашлось, но не то** — в карточке появляется предупреждение «⚠ Название
  совпало не точно. Возможно, вы имели в виду…». Проверка идёт по **исходному
  тексту пользователя**: если в нём были значимые слова, которых нет в найденном
  названии («реван»), значит поиск нашёл похожее, но не тот сериал.

Нажатие на название перезапускает поиск уже по нему — без ручного ввода.
Укороченные варианты запрашиваются только при подозрении на неточность, поэтому
обычный поиск не становится медленнее.

### 3.5-бис Что именно качать: серия, сезон или фильм

Сезон на трекере часто лежит одной раздачей из 10–20 файлов. Поэтому «скачать»
идёт в два шага:

1. **Поиск и уточнение.** Агент ищет по названию и предлагает выбрать
   качество и озвучку — только из того, что реально есть под остальные условия.
   Варианты считаются **с учётом уже заданных условий**: если в 4-м сезоне нет
   720p, кнопки «720p» не будет (раньше агент предлагал его, а после нажатия
   честно отвечал «ничего не подошло»). Кнопки сгруппированы подписями
   **Качество**, **Озвучка**, **Серии** — видно, что к чему относится.

   Под каждым вариантом видно, **что он реально даёт** — вес, сиды и возраст
   лучшей раздачи:

   ```
   Доступно с учётом остальных условий:
   • 1080p — 5 раздач, лучшая: 36,8 ГБ · 12 сидов · 2 дня назад
   • 720p — 2 раздачи, лучшая: 6,1 ГБ · без сидов · 3 недели назад
   ```

   Иначе «1080p» и «1080p» выглядят одинаково, хотя одна мёртвая, а вторая
   на 40 ГБ.

   Если выбранное не подходит, агент не повторяет тот же список, а показывает
   доступное **при остальных условиях** и даёт кнопки «Без учёта качества» /
   «Без учёта озвучки».

3. **Выбор серий.** Как только качество и озвучка определены, агент забирает
   состав раздачи со страницы трекера (`get_file_list`, лимит `.torrent` не
   тратится) и показывает кнопки `Серия 1 · 3,3 ГБ` … `Серия 8`, причём
   **выбор множественный** — отметьте несколько галочками. Отмеченная серия
   видна сразу: в квадратике появляется `✓`, а кнопка внизу считает количество
   и сумму (`Скачать выбранные (3 · 10,8 ГБ)`). На карточке видны сиды, вес
   раздачи, свободное место и каталог. Нажатие **сразу ставит в Transmission** —
   второго вопроса «поставить в очередь?» нет.
   Если серия названа в запросе или текстом в чате («только 3 серия»),
   этот шаг пропускается.

   **Пачка на несколько сезонов.** Сезон на трекере часто лежит одной раздачей
   со всеми сезонами («1-4 сезоны: 1-40 серии из 40»). Тогда показываются
   только серии **сезона задачи**: заголовок говорит
   `В раздаче 10 серий (сезон 2), а в пачке сезоны 1–4 — что качаем?`, кнопка
   «Весь сезон 2» берёт ровно этот сезон, а выбор сверяется по паре
   (сезон, серия). Раньше сверялся только номер серии: одно нажатие «Серия 1»
   ставило в очередь по файлу из каждого сезона — четыре файла и 23 ГБ вместо
   одного.

4. **Карточка подтверждения.** Она нужна, только когда агент выбрал раздачу сам
   (один файл, фильм) или когда вы взяли **другой вариант** из списка
   («Взять вариант 2»). Это полная информация перед постановкой в очередь:

   ```
   Раздача: Тед Лассо (4 сезон: 1-10 серии из 10) / Ted Lasso / 2026 / ПМ (NewComers) / WEB-DL (1080p)
   • Сиды: 12 · пиры: 3 · обсуждали 42
   • Качество: 1080p, WEB-DL
   • Озвучка: ПМ (NewComers), СТ
   • Сезон 4, серия 7
   • Год: 2026
   • На трекере: 36,8 ГБ · залит 2 дня назад · залил NewComers
   • Что качаем: 1 файл — Ted.Lasso.S04E07.1080p.WEB-DL.NewComers.mkv
   • Вес выбранного: 3,3 ГБ
   • Вес всей раздачи: 36,8 ГБ
   • Диск «EAGET»: свободно 204,9 ГБ из 223,5 ГБ (резерв 5 ГБ)
   • Места хватает
   • Куда: /Volumes/EAGET/torrents
   ```

   Сиды, пиры, вес, возраст, автор и число комментариев — это то, по чему
   решают, брать раздачу или нет, поэтому они стоят в карточке, а не в
   служебном журнале. Если сидов нет, карточка сразу предупреждает:
   **«⚠ Сидов нет — качать будет нечем. Лучше взять другую раздачу»**
   (а при 1–2 сидах — «⚠ Мало сидов (2) — скорость будет низкой»).

   Кнопки: `Поставить в Transmission`, `Скачать весь сезон` (если выбрана серия),
   а в группе **Раздача** — `Подробнее` и `Открыть на трекере` (см. 3.5-тер),
   `Отмена`.

Если серия названа прямо в запросе («… 7 серия»), шаг выбора пропускается —
сразу показывается карточка с этой серией. Если такой серии в раздаче нет,
агент честно говорит об этом и предлагает выбрать из имеющихся.

**Как качается одна серия.** В Transmission передаётся `files_wanted` с индексами
файлов этой серии (видео плюс субтитры того же эпизода), остальные помечаются
ненужными — Transmission качает 3,3 ГБ вместо 36,8 ГБ. Проверено на реальной
раздаче: из 10 файлов выбран один, и в памяти агента сохраняется именно серия 7
(а не «пачка 1–10»), иначе следующая проверка решила бы, что серии 8–10 уже есть.

Вес берётся не из строки на трекере, а из самого `.torrent` (bencode), поэтому
это точное число байт — по нему же считается, хватает ли места на диске.

### 3.5-кватер Подробности и ссылка на раздачу

Три вещи, которые не меняют задачу, а помогают решить «тот ли это фильм».

**Кнопка «Подробнее»** (группа «Раздача») открывает окно с тем, чего нет в
названии: жанр, режиссёр, в ролях, «О фильме», видео и аудио (5.1 или стерео,
x264 или x265), вес, сиды, даты. Данные берутся инструментом трекера
`get_torrent_details` (он разбирает `details.php`), а не выдумываются моделью.

Кнопка есть **на каждом шаге, где уже известна конкретная раздача**, а не только
в карточке подтверждения: читать про фильм хочется до того, как выбраны качество
и озвучка.

| Где | О какой раздаче подробности |
|---|---|
| «какой именно фильм?» (список похожих) | о самом вероятном варианте |
| «какое качество?» / «какую озвучку?» | о лучшей под текущие условия |
| «под эти условия ничего не подошло» | о лучшей из найденных |
| «нашлись только экранки» | об этой экранке |
| карточка подтверждения и список серий | о выбранной раздаче |
| «Скачано на диск» | о скачанной раздаче — видно, что смотреть |

Важно, что это **чтение, а не ход переписки**: клиент запрашивает
`GET /api/torrent/<id>/details` и рисует окно, ничего не отправляя в чат. Иначе
предыдущее сообщение с кнопками считалось бы отвеченным и подтвердить скачивание
было бы нечем. Запрос идёт только по нажатию (поиск не ждёт лишний поход через
шлюз) и кэшируется на 10 минут. Окно открывается сразу, с подписью «читаю
страницу раздачи»: на холодном шлюзе ответ может идти секундами, а молчаливая
кнопка «открываю…» выглядит как «ничего не произошло».

**«Открыть на трекере»** — обычная ссылка `details.php?id=…` в новой вкладке:
комментарии к раздаче («битый звук», «экранка») читают именно там. Кнопка-ссылка
отличается от обычной тем, что клиент рисует `<a>`, а не `<button>`: на телефоне
это открывается в браузере, а не внутри приложения.

**Ссылка вместо названия.** Если прислать в чат готовую ссылку
(`…/details.php?id=1234567`, а также `download.php?id=…` и вообще
`kinozal.<домен>/…?id=…`), поиск по названию и модель не нужны: агент открывает
страницу раздачи, собирает из неё `Torrent` (название, вес, сиды, качество) и
сразу показывает то же, что показал бы после поиска — выбор серий или карточку
подтверждения. Это частый способ получить раздачу («держи ссылку»), и он
работает даже когда название на трекере написано иначе.

### 3.5-квинта Экранки в выдачу не попадают

CAM/TS/TC/SCR — копия, снятая с экрана: картинка и звук хуже релиза. Такие
раздачи по умолчанию **не предлагаются и не скачиваются** (задача «следи за
новыми сериями» тоже их игнорирует): правило живёт в `core/parsing.is_screener`
и `core/matching.filter_candidates`, поэтому действует одинаково для поиска,
уточнений и мониторинга.

Узнаём экранку по пометке в **зоне качества** (после года в названии), поэтому
фильм «Cam» или сериал со словом «TS» в названии не выпадает из выдачи по
ошибке. Если по названию есть **только** экранки, агент не говорит «ничего не
нашлось», а честно объясняет и даёт кнопки **«Показать экранку»** (добавляет
`params["screener"]`, после чего фильтр снимается) и «Следить за нормальной
раздачей». В запросе это же можно сказать словами: «экранку» / «камрип» — поле
`screener` в разборе запроса и уточнениях переживает правки задачи.

### 3.6 Память «что уже скачано» и «новая серия»

Скачанное пишется в таблицу `downloads` (id раздачи, сериал, сезон, серия,
качество, озвучка, дата заливки). По ней:

* уже скачанная раздача не предлагается и не качается повторно;
* «новая серия» = раздача, которой раньше не было, **и** её номер серии выше
  максимального известного в том же сезоне (для фильмов — по дате заливки).

Многосезонные пачки («1–4 сезоны: 1–44 серии из 44») в нумерацию не попадают:
в них счёт сквозной, и «44» ничего не говорит о четвёртом сезоне — иначе новая
11-я серия считалась бы уже скачанной. При создании периодической задачи
фиксируется «базовая линия» (что есть сейчас), поэтому первая проверка не
присылает уведомление про все 30 раздач сразу.

### 3.7 Периодические задачи

Периодическая задача — это сохранённое намерение: «проверяй вот это и делай вот
так». Она живёт независимо от переписки, у неё свой интервал и свой режим.

**Условия задачи — это условия, а не пожелания.** Раздача считается
подходящей только если совпало всё: название, год, качество, озвучка, сезон.
Ни в карточке задачи, ни на проверках нет подстановки «похожего вместо
подходящего»:

* если под условия ничего нет — агент честно пишет `По вашим условиям (год 2026,
  качество 2160p) на трекере сейчас ничего нет — буду проверять и сообщу, когда
  появится`;
* найденное «по названию, но с другими параметрами» показывается отдельным
  списком **«Похожие по названию, но с другими параметрами»** и никогда не
  считается найденным;
* следить всё равно можно — кнопками **«Качать сразу и сообщать» / «Только
  сообщать»** (это и есть «строго по моим условиям»), а если условия
  кажутся слишком узкими — отдельными кнопками «Следить без года», «без
  качества», «без уточнений» или «Это «Другое название»». Каждое ослабление —
  явное действие человека, а не догадка агента.

Пример: задача «Прайм-тайм 2026, 4K», а на трекере есть только «Прайм-тайм»
2024 года и «Злодейка прайм-тайма» 2024. Раньше агент подставлял фильм 2024 как
найденный и при подтверждении скачивал его; теперь он сообщает, что под условия
ничего нет, показывает похожие отдельным списком и ждёт настоящую раздачу 2026
года в 4K.

**Задача не создаёт других задач.** Любая периодическая задача — это та же
запись в базе: «Сделать периодической» переводит существующую задачу в
`periodic` (тот же `id`, та же переписка), а не заводит двойника. Новые задачи
появляются только из сообщения в чате.

**Как заводится (два шага).**

1. Кнопка **«Периодически»** + запрос. Модель разбирает его в параметры:
   название, сезон, `episode_from` («начиная с третьей»), качество, озвучку,
   интервал (`interval_minutes`). Если период не назван — **раз в сутки**
   (`DEFAULT_INTERVAL_MINUTES=1440`); изменить потом можно словами
   («проверяй раз в час»).
2. **Шаг выбора варианта.** Агент ищет по трекеру и показывает, что подходит
   под условия, а что — «похоже по названию, но с другими параметрами».
   Кнопки:

   ```
   [Ваш вариант]          Следить строго: качество 1080p, серия 4      ← условия в подписи
   [Похожие варианты]     Следить: серия 3 · 2026 · 1080p · 7,74 ГБ     Подробнее
                          Следить: серия 2 · 2026 · 1080p · 7,09 ГБ     Подробнее
                          Следить: серия 1 · 2026 · 1080p · 7,7 ГБ      Подробнее
   [Отмена]
   ```

   На каждый похожий вариант — своя кнопка «Следить: …» и «Подробнее» (окно
   с жанром, описанием, сидами и ссылкой на страницу раздачи: решить «это оно
   или нет» можно до выбора). Режим здесь не спрашивается.
3. **Шаг подтверждения.** После выбора варианта — резюме:

   ```
   Вы выбрали: «Выживалити: Легенда Альфа».
   • Условия: качество 1080p, серия 4
   • Ждём: 1080p, жду серию 4
   • Проверка: каждые 30 минут
   • Сейчас подходит: ничего — сообщу, когда появится
   • Первая проверка в 18:10

   [ Качать сразу и сообщать ] [ Только сообщать ] [ Другой вариант ] [ Отмена ]
   ```

   «Другой вариант» возвращает к списку — переключиться можно сколько угодно.
4. При старте фиксируется **базовая линия** по итоговым условиям (они могли
   измениться, если выбран похожий вариант): какие серии уже лежат на трекере.
   Они новыми не считаются — иначе первая же проверка прислала бы уведомление
   про весь сезон.
5. Дальше задача в состоянии `monitoring`, `next_check_at` = сейчас + интервал.

**«С 4 серии» значит, что раздача с 1–3 сериями не подходит** — даже если
название и качество совпали. Раньше такая раздача показывалась как «подходит
(серия 4)», хотя в ней была только третья серия.

**Что происходит на каждой проверке** (шедулер просыпается раз в 20 секунд и
берёт задачи, у которых наступило время; каждая задача — отдельная корутина,
они не мешают друг другу и лимита на их число нет):

1. Поиск по трекеру и фильтрация по параметрам задачи.
2. Для каждой найденной раздачи считается, **новая ли она**:
   * сериал с одним сезоном — сравнивается **номер серии**: раздача новая,
     если в ней есть серия ≥ той, которую ждём;
   * пачка на несколько сезонов — по дате заливки (нумерация там сквозная);
   * фильм/музыка/книга — по дате размещения.
3. «Какую серию ждём» (`next_episode`) = `max(episode_from,
   максимальная скачанная серия + 1)`. Поэтому задача «качай новые, начиная с
   третьей» после третьей ищет четвёртую, а не третью повторно.
4. Если нового нет — тишина (в журнал проверок пишется «0 новых»).
5. Если есть:
   * **пачка серий, а какую брать — не сказано** (задача без серии, без
     сезона и без качества, а в раздаче 10–40 серий): пачка **не качается
     молча**. Приходит уведомление «раздача с сериями: 20 серий на 120 ГБ, из
     них новых 15» с кнопками **«Скачать всю пачку»** и **«Выбрать серии»**
     (тот же выбор по сезонам). Так же и в режиме «качать сразу»: 20 файлов
     без спроса — это под сотню гигабайт. Уведомление повторяется только
     когда пачка выросла;
   * **режим «качать сразу»** — сначала состав раздачи проверяется **по
     странице трекера** (`get_file_list`, суточный лимит `.torrent` не
     тратится). Если нужной серии там нет — `.torrent` не качается вовсе:
     задача просто ждёт следующей проверки. Если есть — `.torrent`
     перекачивается (на трекере та же раздача обновляется новыми выпусками,
     старый файл уже не содержит нужную серию), из него выбираются **только
     новые серии**, они ставятся в Transmission, и приходит уведомление о том,
     что сделано;
   * **режим «только сообщать»** — приходит уведомление со списком находок и
     кнопками «Скачать N»; ничего не качается, пока пользователь не нажмёт.

Так же, как и в разовых задачах (`_present_candidate` → `_listing_entries`),
`.torrent` запрашивается ровно один раз — когда раздачу действительно ставят в
очередь. Раньше периодическая проверка качала `.torrent` «на всякий случай»
перед каждым решением, и лимит `.torrent` в сутки мог кончиться на проверках, а
не на просмотре. Решение по странице принимается только когда номера серий
видно в именах файлов («01. Звёзды в джунглях.S03.mkv»); если имена без номеров,
идём обычным путём и смотрим настоящий `.torrent` — иначе можно было бы не
скачать нужную серию.

**Почему номер серии, а не id раздачи.** На kinozal одна и та же раздача
обновляется по мере выхода выпусков: «3 сезон: 1-2 выпуски из 14» → «1-3» →
«1-4». Если считать «новое» по id, второй выпуск никогда бы не скачался.
Поэтому приоритет у номера серии, а id служит только для неэпизодического
контента (фильмы, музыка).

**Сколько серий ставится за раз.** В авторежиме ставится не больше трёх новых
серий за проверку: если «догонять» пришлось много (в раздаче 10 свежих серий на
60 ГБ), агент спросит, а не зальёт всё. Порог — `Agent.auto_episodes_max`.

**Что именно скачивается из пачки.** Если в раздаче 14 файлов и нужна третья
серия, в Transmission передаётся `files_wanted` с индексом одного файла:
качается 1,9 ГБ вместо 26 ГБ. Если появились сразу две новые серии — обе.
Имя серии определяется по имени файла: `S03E07`, `4x07`, «серия 7», «выпуск 7»
и ведущий номер (`01. Название.avi`).

**Раздача попадает в «Скачано» только когда докачалась.** Запись в памяти
агента создаётся сразу при постановке в очередь (иначе он не знал бы, что
раздача уже взята, и качал бы её повторно), но в списке «Скачано на диск» она
появляется после того, как Transmission скажет «готово»: у записи есть
`done_at`, и его ставит опрос прогресса (`refresh_progress`) или проверка при
постановке. До этого раздача видна только в «В работе», со своим прогрессом —
не в двух местах сразу.

**Одна раздача — одна запись.** В «Скачано на диск» раздача показывается одной
строкой, даже если из пачки взяли весь сезон: `сезон 2, серии 1–5`. Какие именно
серии скачаны, лежит в колонке `episodes` записи (JSON-список
`[{"season": 2, "episode": 1}, …]`), а `season`/`episode` — «последняя серия».
Раньше на каждую серию писалась своя строка, и «весь сезон» превращался в пять
записей в списке. Прогресс («какую серию ждём») считается по `episodes`, поэтому
удаление файлов и повторные скачивания работают как раньше. Старые базы
сливаются автоматически при старте (миграция в `Store._migrate`).

**Память и удаление файлов.** Запись о скачанном делается **после** постановки
в Transmission и защищена от ошибок: если запись почему-то не удалась, торрент
остаётся в очереди, а в журнале отладки появляется «скачанное не записано в
память». Так не бывает «торрент в Transmission есть, а агент про него не знает»
— именно этот случай однажды случился из-за падения разбора плана серий.

 Каждая скачанная серия записывается отдельной
строкой (раздача + сезон + серия), поэтому одна и та же раздача может дать
несколько записей. Из этой памяти и считается `next_episode`.

Удаление файлов **не стирает память**: запись помечается удалённой
(`deleted_at`), пропадает из списка «Скачано на диск», но продолжает считаться
прогрессом. Поэтому если вы посмотрели третью серию и удалили её, чтобы не
занимать место, задача «качай новые, начиная с третьей» продолжит с четвёртой, а
не скачает третью заново. Если ту же серию скачать заново вручную — запись
«оживает», дубликата не появляется.

**Управление.** В карточке «В работе» у задачи есть «Проверить» и «Отменить»,
у периодической — ещё «Журнал». Отмена переводит задачу в `cancelled` и
прекращает проверки.

**Отмена отменяет и скачивание.** Если раздача уже стоит в очереди
Transmission, «Отменить» убирает её оттуда и стирает недокачанное (без корзины,
как и «Удалить»): раньше задача закрывалась, а торрент продолжал качаться сам по
себе, занимать место и висеть в списке. В ответ приходит
`Задача «…» отменена. Раздача убрана из очереди, удалено объектов: 2,
освобождено 640 МБ`. Уже докачанные файлы не трогаются — они попадают в
«Скачано на диск», и задача просто закрывается. Запись о недокачанном из памяти
удаляется целиком, чтобы раздачу можно было взять снова.

Под сообщением в чате у задачи, которая **уже следит**, остаётся только
«Проверить сейчас»: отмена живёт в карточке «В работе» — один пульт на одно
действие, чтобы не было двух кнопок «Отменить» на экране. Пока задача ждёт
подтверждения или качается, «Отменить задачу» остаётся и в чате: карточка может
быть вне поля зрения (на телефоне панель закрыта).

**Уточнение внутри задачи меняет её настройки, а не открывает новый поиск.**
Написать в открытой периодической задаче «только 4к», «нужен LostFilm»,
**«проверяй раз в сутки»** или **«только сообщай»** — значит поправить саму
задачу: фильтры, период проверки и режим. Задача остаётся в работе, расписание
пересчитывается, в ответ приходит

```
Уточнил: проверка — раз в сутки.
Задача «…» продолжает следить раз в сутки и сразу качать.
• Ждём: 4K (2160p)
• Следующая проверка завтра в 11:43
```

и кнопка «Проверить сейчас». Период и режим — это настройки задачи, а не
параметры поиска (в `params` они не лежат), поэтому раньше они терялись при
уточнении: «проверяй раз в сутки» уходило в «уточните, что поправить».
А до этой правки любое уточнение вообще шло в разовый выбор раздачи: на трекере
ничего не находилось, задача попадала в `not_found` — то есть в «Завершённые», —
и проверки прекращались (шедулер берёт только `monitoring`). Если уточнение
меняет название, базовая линия старого сериала сбрасывается: иначе задача ждала
бы серию, которой у нового сериала нет.

**Видно, что задача живая.** В карточке периодической задачи появляется строка
последней проверки — `проверка: 12:40 — нового нет · следующая 13:40`, рядом —
**что именно отслеживается** (`1080p, сезон 3, жду серию 2`), а кнопка
**«Журнал»** открывает последние проверки (когда, сколько подходящих раздач
нашлось, сколько из них новых, какие именно). Ответ на «Проверить сейчас»
говорит то же словами: `Проверил «…»: нового нет (подходящих раздач: 1).
• 1080p, сезон 3, жду серию 2 • следующая проверка в 11:30`. Данные пишутся в
таблицу `checks`, поэтому не приходится гадать, работает мониторинг или молча
встал.

**Скачивание повторяется само.** Если трекер не отдал `.torrent` (например,
кончился суточный лимит), задача запоминает раздачу в
`params.pending_download` и **пробует снова на каждой проверке** — в том числе
когда нового ничего нет. Поэтому после сброса лимита достаточно дождаться
очередной проверки (или нажать «Проверить сейчас»), и файл скачается; раньше
задача отвечала «нового нет» и молчала дальше, потому что раздача считалась
уже найденной. Пока повтор не удался, в карточке видно `скачивание ждёт повтора
(причина)`. Отложенное снимается через 7 дней, чтобы не тянуть вечно мусор.

**Ошибка не висит вечно.** `last_error` очищается, как только проверка прошла
успешно: иначе объяснение вроде «использовано количество торрент-файлов в
сутки» оставалось в карточке навсегда и выглядело как «задача сломана».
Скачивание запишет свою ошибку заново, если она правда повторится.

**Название сравнивается по словам, а не по подстроке.** Это важнее, чем
кажется: предлог «на» находится внутри слова «крепостная», и раньше запрос
«Ставка на любовь» совпадал с раздачей «Крепостная … Желанная любовь»
(3 сезон: 1-24 серии). Из-за ложного совпадения базовая линия периодической
задачи записывалась как «24 серии уже есть», задача ждала 25-ю серию и не
скачивала ничего. Теперь обязательны все значимые слова (слова из 1–2 букв
выбрасываются, окончания снимаются: «игра» ≈ «игры»), пропуск одного слова
прощается только в запросах из трёх+ слов и только не первого.



Каждая задача живёт в своей корутине (`_scheduler_loop` → `_run_check_isolated`),
падение одной не влияет на другие, лимита на количество нет. Шедулер просыпается
раз в 20 секунд и берёт задачи, у которых наступило `next_check_at`.

Найдено новое:
* режим «только сообщать» — уведомление + кнопки «Скачать 1/2/3», задача
  продолжает жить;
* режим «качать сразу» — скачивает (до 3 новых за раз), ставит в Transmission,
  сообщает.

Уведомления идут по трём каналам сразу (`core/notify.py`, `core/push.py`):
центр уведомлений в интерфейсе (SSE), системные уведомления macOS, Web Push.

### 3.7-тер Видно процесс загрузки

Transmission RPC не умеет присылать события — только отвечать на запросы.
Поэтому агент опрашивает прогресс сам (`Agent.refresh_progress`, раз в 5 секунд),
и задача **не прыгает в завершённые сразу** после постановки в очередь:

* состояние `downloading` — пока файл не дошёл до 100%;
* в карточке задачи и в списке «Скачано на диск» виден прогресс-бар и подпись
  `42,5% · 1 МБ/с · осталось 10 мин · 1,7 ГБ из 4 ГБ`;
* когда загрузка закончилась — задача уходит в «Завершённые», в чат приходит
  «Скачано: «…» (3,7 ГБ)», уходит уведомление в центр/систему/Web Push;
* если раздачу удалили из очереди вручную — задача тоже закрывается, а не висит.

Задача уходит в «готово» только когда Transmission прямо сказал `done`. Раньше
**пустой ответ RPC** (прогресс только что добавленной раздачи ещё не пришёл)
считался завершением: задача оказывалась в «Завершённых», переставала
опрашиваться и оставалась «готовой», пока файл качался. Теперь опрос проверяет
и такие задачи: если торрент всё ещё качается, задача возвращается в
«скачивание».

Объём считается по **выбранным файлам** (`size_when_done`), а не по всей
раздаче: качаем одну серию — видим «из 3,7 ГБ», а не «из 29 ГБ».

### 3.7-бис Журнал отладки

В «Служебном» есть кнопка **«Журнал отладки»**. Она открывает окно с тем, что
агент делал на самом деле — не HTTP-логи, а суть:

| Категория | Что видно |
|---|---|
| `llm` | запрос к модели и её ответ: параметры разбора, тексты, вызовы инструментов, токены, время |
| `mcp` | какой инструмент трекера вызван, с какими аргументами и что вернул (сколько символов, текст ответа) |
| `gate` | запросы к kinozal.me через шлюз: адрес, статус, прошёл ли через браузер или curl_cffi, отказы Cloudflare |
| `transmission` | постановка в очередь, каталог, размер, отказы «не хватает места» |
| `agent` | что модель поняла из запроса, сколько раздач нашлось, что выбрано, результат проверки периодической задачи |
| `log` | предупреждения и ошибки из логов модулей |

В окне есть фильтры по категориям, раскрытие подробностей по клику, автообновление
раз в 4 секунды, кнопки «Обновить», «Скопировать» (в буфер обмена простым текстом)
и «Очистить». Длинные значения обрезаются, чтобы список оставался читаемым.

Журнал **общий для процессов**: шлюз Cloudflare работает отдельным процессом, но
пишет в тот же файл `data/debug.jsonl`, поэтому его события видны в интерфейсе
наравне с вызовами модели. Файл ограничен последними 3000 событиями, лежит в
`data/` (не в репозитории) и его можно удалить в любой момент — на работу агента
это не влияет. Ключи и пароли в журнал не попадают никогда.

### 3.7-тер Удаление раздачи вместе с файлами

В картотеке, в списке «Скачано», у каждой раздачи есть кнопка **«Удалить»**.
Она открывает **окно подтверждения** с точной информацией (размер, папка,
`.torrent`, оговорка про память агента), и только по кнопке «Удалить навсегда»
делает три вещи:

1. убирает раздачу из очереди Transmission (без его собственного удаления
   данных);
2. стирает файлы раздачи и её недокачанную часть с диска;
3. удаляет `.torrent`-файл и запись из памяти агента (скачанное больше не
   считается скачанным).

Подтверждение — **окно**, а не сообщение в чате: кнопку «Удалить» нажимают в
картотеке, а сообщение появлялось в чате (на телефоне чат под панелью), и
второй шаг легко не заметить. Со стороны это выглядело как «удаление не
работает»: раздача оставалась на месте, и человек жал «Удалить» ещё раз.
Серверный сценарий (`delete_download` → `confirm_delete`) не изменился — веб
рисует его окном, а бот сможет показать кнопками в чате.

**Почему не штатное удаление Transmission.** На macOS Transmission перемещает
данные в `.Trashes` на том же томе, и место не освобождается, пока корзину не
очистят руками. Поэтому данные стирает сам агент — обычными `os.remove` и
`shutil.rmtree`, которые корзину не используют. Проверено на реальной раздаче:
после удаления свободное место на диске вернулось сразу, а `.Trashes` не вырос.

**Защита от ошибок.** Пути приходят из Transmission RPC, поэтому каждый путь
приводится к реальному (`realpath` — снимает `..` и симлинки) и обязан лежать
внутри разрешённых корней: каталога загрузок, его `.incomplete` и папки
torrent-файлов. Сам корень удалить нельзя. Всё, что не прошло проверку, не
удаляется и попадает в отчёт как «не тронуто (вне разрешённых папок)».

Отдельно решена гонка: Transmission убирает раздачу не мгновенно, и файл мог
дописаться уже после удаления — папка появлялась снова. Теперь агент ждёт
исчезновения раздачи из очереди, а затем ещё до трёх раз дочищает остатки.

### 3.7-кватер Место на диске: занято, наши файлы и корзина

В «Служебном» диск показан тремя строками, и это не избыточность:

```
диск          EAGET · свободно 204,9 ГБ из 223,5 ГБ
занято        18,6 ГБ · наши файлы 0 Б
не наши файлы 18,6 ГБ — чужие данные или корзина диска
```

Зачем: macOS в Finder не показывает содержимое `.Trashes` на внешнем томе, а
Transmission при штатном удалении перемещает данные именно туда. В итоге место
занято, диск «пуст», и цифра выглядит враньём. Теперь видно, сколько занято
всего, сколько из этого — загрузки агента и torrent-файлы, и что остаток
приходится на что-то ещё. Место вернётся после **«Очистить корзину»** в Finder
(она чистит и корзины томов) или командой
`sudo rm -rf /Volumes/<диск>/.Trashes/501/*`.

Наши файлы считаются отдельно (`core/storage_target.dir_size`) с ограничением по
времени: обход 200 ГБ ради строчки в интерфейсе недопустим, поэтому при
превышении бюджета значение помечается как приблизительное (`≈`).

### 3.7-квинк Простой, сон и «всё подвисло после того, как я не подходил»

Три вещи мешали отклику после долгого простоя — все три устранены.

1. **Диск засыпал.** На этой машине `pmset disksleep 10`: через десять минут
   тишины система паркует внешний SSD. Transmission блокируется на записи,
   `statvfs`/проверка записи виснут на секунды, и первый же запрос RPC
   отваливается по таймауту (в журнале это `TransmissionTimeoutError`, пачкой
   по 20 секунд). Теперь оба сервиса запускаются под
   `caffeinate -i -m` — пока агент работает, система не засыпает от простоя, а
   диск не паркуется (`pmset -g assertions` показывает `PreventDiskIdle`).
   Проверить: `pmset -g assertions | grep caffeinate`. Отключить: `CAFFEINATE=0`.
   Вместо caffeinate можно системно: `sudo pmset -a disksleep 0`.
2. **RPC ждал свой полный таймаут.** У клиента `transmission-rpc` таймаут 20 с,
   а после простоя мёртвое соединение как раз и висит до конца. Теперь каждый
   вызов идёт через `Transmission._run`: бюджет 8 с (постановка — 15 с), при
   таймауте соединение сбрасывается и **повторяется один раз** с новым клиентом
   — обычно второй раз отвечает мгновенно.
3. **Проверка диска подвешивала весь процесс.** `status()` синхронно делал
   `statvfs` + проверку записи и обход каталогов — на спящем диске это блокировка
   цикла событий (встаёт чат, SSE, опрос прогресса). Теперь это отдельный поток
   с бюджетом 6 с и кэшем на 10 с; сам `status()` кэшируется на 5 с, а список
   скачанного — на 3 с (картотека опрашивает его каждые 5 с).

Плюс мелочи в ту же сторону:

* браузерная часть ничего не опрашивает, пока вкладка скрыта
  (`visibilitychange`) — телефон в кармане не дёргает сервер каждые 5 секунд;
* шлюз сам обновляет `cf_clearance` раз в 12 минут (`GATE_KEEPALIVE_MINUTES`),
  поэтому первый запрос к трекеру после простоя не ждёт, пока Chrome заново
  пройдёт challenge (это занимало до 77 секунд: `browse.php` 403 → challenge →
  200).

**Что всё-таки останавливает работу.** Настоящий сон машины (аккумулятор,
закрытая крышка) останавливает всё — и агент, и Transmission: процессы
просыпаются вместе с системой, пропущенные проверки идут сразу после
пробуждения. На питании от сети `sleep 0`, поэтому этого не происходит.

### 3.8 Интерфейс

Старая киноплёнка: сепия, зерно, мерцание проектора, перфорация по краям,
винетка. Без внешних шрифтов и картинок — всё рисуется CSS, поэтому работает и
офлайн, и на телефоне.

Декоративные «царапины» живут только в полосе перфорации по краям экрана
(`mask-image` вырезает середину): раньше они шли вертикальными линиями через
всю страницу и попадали прямо на текст сообщений — читалось как случайная
полоса. На телефоне, где переписка занимает всю ширину, царапины выключены.

* две кнопки режима — **Разово** и **Периодически**;
* картотека слева (на телефоне — выдвижная панель) из трёх разделов, и это
  **разные вещи**:
  * **В работе** — активные задачи: ищут, ждут подтверждения, следят за новым;
  * **Завершённые** — задачи, которые закончились: готово, отменено, не найдено,
    ошибка (история решений, а не файлов);
  * **Скачано на диск** — то, что реально лежит в Transmission и на внешнем
    диске; отсюда же удаление.

  У каждого раздела свой счётчик и своя кнопка **«показать/скрыть»**, состояние
  запоминается в браузере. Пустой список показывает заглушку («активных задач
  нет») и от этого не схлопывается: у кнопки всегда есть видимый эффект. У
  каждой задачи в «В работе» и «Завершённых» есть кнопки «Проверить» и
  «Отменить», у периодической — ещё и «Журнал» (последние проверки);
* в карточке раздачи — группа **Раздача**: `Подробнее` (жанр, актёры, описание,
  видео/аудио — в отдельном окне, без хода в переписку) и `Открыть на трекере`
  (ссылка на `details.php`, открывается в новой вкладке);
* колокольчик — киножурнал уведомлений;
* «Доступы» — логин/пароль kinozal и RPC Transmission (пишутся в SQLite и
  перекрывают `.env`, перезапуск не нужен);
* мобильная раскладка с `safe-area-inset` под iPhone.

`app.js` не собирается и не минифицируется: страница обязана открываться и с
телефона в чужой сети, и с самоподписанным сертификатом. Поэтому окно
«Подробности» рисуется тем же `document.createElement`, что и сообщения: новых
зависимостей не появилось.

## 4. Настройки (`.env`)

| Переменная | Смысл |
|---|---|
| `SITE_HOST`, `SITE_PORT` | адрес сайта (по умолчанию `0.0.0.0:8000`) |
| `SITE_TLS` | `1` — HTTPS с самоподписанным сертификатом |
| `SITE_TLS_NAMES` | адреса в сертификате (IP мака в домашней сети) |
| `SITE_PASSWORD` | пароль входа; пусто — без пароля (не оставлять при пробросе наружу!) |
| `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL` | ключ и модель (`deepseek-flash`) |
| `KINOZAL_USERNAME`, `KINOZAL_PASSWORD` | учётка трекера |
| `KINOZAL_BASE_URL` | адрес трекера (`https://kinozal.me`); из него же собираются ссылки «Открыть на трекере» |
| `TRANSMISSION_HOST/PORT/USERNAME/PASSWORD` | RPC Transmission |
| `TRANSMISSION_DOWNLOAD_DIR` | внешний диск для загрузок (`/Volumes/<диск>/torrents`) |
| `TORRENTS_DIR` | папка для `.torrent`-файлов на том же внешнем диске |
| `TRANSMISSION_MIN_FREE_GB` | сколько места обязано остаться после скачивания |
| `TRANSMISSION_SPEED_LIMIT_MBPS` | потолок скорости скачивания в МБ/с (по умолчанию 70; `0` — без ограничения): запас скорости не даёт записи на внешний диск заморить сам демон |
| `TRANSMISSION_CACHE_MB` | кэш записи Transmission в МБ (по умолчанию 32): крупные пачки вместо частых мелких |
| `GATE_PORT`, `GATE_HEADLESS`, `GATE_PROFILE_DIR` | шлюз Cloudflare |
| `GATE_KEEPALIVE_MINUTES` | как часто шлюз сам обновляет `cf_clearance`, пока работает (по умолчанию 12; `0` — не обновлять) |
| `CAFFEINATE` | `1` — держать систему и внешний диск бодрыми, пока агент работает (по умолчанию; `0` — не мешать) |
| `DEFAULT_INTERVAL_MINUTES` | период проверки, если он не назван в запросе (по умолчанию **1440** — раз в сутки) |
| `MIN_INTERVAL_MINUTES` | ближе, чем раз в столько минут, задача не проверяет |
| `CONTEXT_MESSAGES` | размер скользящего окна переписки (по умолчанию 20 сообщений) |

Значение из окружения важнее строки в `.env`.

## 6. Ограничения и что требует внимания

1. **Учётка kinozal.me обязательна.** Без входа сайт вместо `.torrent` отдаёт
   страницу «Вход», и агент честно сообщает об этом в чате. Логин и пароль
   задаются в `.env` (`KINOZAL_USERNAME`, `KINOZAL_PASSWORD`) или прямо в
   интерфейсе: кнопка **Доступы** → «Проверить». Там же видно, принял ли сайт
   пару — трекер отвечает внятно («Неверно указан пароль для имени …»).
2. **Web Push и service worker** требуют доверенного HTTPS: с недоверенным
   сертификатом браузер отказывается регистрировать service worker (в консоли
   «SSL certificate error»), и push не работает. Чтобы включить, сертификат
   проекта добавляется в доверенные один раз на машине, где открывают сайт:

   ```bash
   security add-trusted-cert -r trustRoot -p ssl \
     -k "$HOME/Library/Keychains/login.keychain-db" data/tls/site.crt
   ```

   Три вещи, без которых это не сработает и на них легко наступить:
   сертификат выпускается с `CA:TRUE` (иначе macOS не даст сделать его
   корневым), политика указывается явно (`-p ssl`), а после установки нужен
   перезапуск браузера. Телефону сертификат ставится отдельно (профиль `.crt`
   из `data/tls/`). На этой машине уже сделано — центр уведомлений, системные
   уведомления macOS и Web Push работают все три.
3. **Chrome шлюза — видимый процесс.** Он настоящий (иначе Cloudflare не
   пустит), окно за пределами экрана. Закрывать его вручную не нужно.
4. **Transmission** хранит пароль RPC в своём keychain, поэтому его нужно
   вписать в `.env` (`TRANSMISSION_USERNAME`, `TRANSMISSION_PASSWORD`) или в
   «Доступы». При смене пароля — там же.
5. Сайт слушает `0.0.0.0` и проброшен наружу: держите `SITE_PASSWORD`
   заполненным.
6. **Не коммитьте `.env`.** В нём ключ модели, пароли трекера и RPC. Файл уже
   в `.gitignore`; в репозиторий попадает только шаблон `.env.example` с
   пустыми значениями и без адресов вашей сети.
7. **Если удалять в самом Transmission, данные уходят в корзину.** Штатное
   удаление в Transmission на macOS перемещает файлы в `.Trashes` на том же
   диске, и место освобождается только после очистки корзины (Finder →
   «Очистить корзину»). Кнопка «Удалить» в агенте работает иначе — стирает файлы
   сразу, без корзины.
8. **Правка `.env` требует перезапуска** (`scripts/run.sh restart`): настройки
   читаются один раз при старте. Логины и пароли kinozal/Transmission — другое
   дело, их можно менять на ходу через «Доступы».
